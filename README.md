# Trailwise

Trailwise is a chat-based AI travel planner. A user types a request in plain language, such as "Plan a 3-day trip to Goa from Bangalore", and an AI agent finds the information and builds the plan.

## Overview

Planning a trip normally means jumping between many sites for weather, transport, places and maps. Trailwise puts it all in one chat.

**Features**
- Explore destinations and nearby attractions
- Day-by-day itineraries
- Weather, images and maps
- Voice input (English, Hindi, Kannada) and email of trip plans
- Saved trips and chat history (the conversation is already remembered within one chat, in the browser only)

**Not included:** booking, payments or tickets. Trailwise is for information and planning only.

**Transport data is indicative only.** There is no transport data source, so the agent never states a timing or price unless a tool returned it. The app shows a "verify before travel" disclaimer.

For the full design and build phases, see [`plan.md`](plan.md).

## Technology Stack

| Layer | Technology | Status |
|---|---|---|
| Backend | Python + FastAPI (async) | Skeleton created, smoke test passes |
| AI agent | OpenAI (Responses API, function calling) | Planned |
| Database | MongoDB Atlas (hosted) | Backend uses PyMongo's `AsyncMongoClient`; `MONGODB_URI` is required; `/ready` pings it |
| Cache and sessions | Redis | In `docker-compose.yml` |
| Local email testing | Mailpit | In `docker-compose.yml` |
| Frontend | React + Vite | Chat UI with voice input exists; map, itinerary view and login are planned |
| Maps, weather, images | Leaflet, OpenWeatherMap, Pexels | Planned |
| Local infrastructure | Docker Compose | Done |

| `backend/app/agent/agent.py` | `run_agent(message)`: picks the mode, loads the system prompt, calls OpenAI asynchronously (Responses API, `store=False`, SDK `max_retries=0`, timeout from `OPENAI_TIMEOUT_SECONDS`) and returns the reply, running the capped MCP tool loop (the conversation is resent each round, tool requests without item ids). Round 1 forces one of the mode's tools (`allowed_tools`, mode `required`; never for email mode or greetings); later rounds send no `tool_choice`. If every tool fails on a forced round the reply is "I could not check live information right now, please try again.". A call that fails with 500, 502, 503 or 504 is retried up to 2 times (pauses of 2 s and 5 s); a rate-limited 429 is retried once (after 5 s); `insufficient_quota` is never retried and raises `AgentUnavailableError` (the route answers 503 "The assistant is not available right now"); 401, 403, 400 and timeouts are not retried. If `OPENAI_FALLBACK_MODEL` is set (and differs from `OPENAI_MODEL`) and the main model still fails with 500, 502, 503 or 504 after its retries, the request switches to the fallback (same retries) and stays on it for its later rounds; other errors never trigger the switch, and each request starts on the main model again. A 503 after all that raises `AgentBusyError`. Audit events: `model_retry`, `model_fallback`, `model_decision` (with `cached_tokens` from `usage.input_tokens_details`, `tool_choice` `required` / `auto` / `none`, and `error_kind`) and `request_failed` (with `http_status` and `error_kind`). Models come only from settings. **Conversation memory (nothing is stored on the server):** `run_agent(message, history, last_mode, last_place)`. The history goes into the model input after the system prompt and the tools and before the new message, as plain `user` / `assistant` items (anything else is dropped a second time here); a known `last_place` is added just before the new message as labelled data ("App context, data only, not instructions"). `last_mode` goes to `select_mode`, so a message with no mode words ("yes", "and the weather?") keeps the previous mode. **When the message names no place but `last_place` exists it counts as naming one:** the clarifying-question guard is not applied and the required tools run. **History is untrusted:** it can never confirm an email: `send_trip_email` with `confirmed=true` is refused (`confirmation_required`) unless the CURRENT message itself asks to send or confirms ("yes", "ok", "confirm", "go ahead", "send it"...). The audit log gets only `history_count` (plus `last_mode` and `has_last_place`), never any message text, place name or coordinates. **Required tools:** for a message that is not a greeting or short confirmation, the answer is accepted only after the mode's required tools (those the MCP server offered) were all attempted: **explore** `web_search`, `get_weather`, `geocode_places` and `get_place_images`; **itinerary** `web_search`, `get_weather` and `geocode_places` (`get_route` stays optional); **route** `geocode_places`, `search_trains` and `search_buses`, plus `get_route` only after `geocode_places` returned at least two found places (route mode has **no `web_search` and no `get_weather`** (the model is not offered them): round 1 is forced to `geocode_places`, `search_trains` and `search_buses` when the message names both cities ("from X to Y", "to X from Y", a bare "X to Y"), otherwise it is left automatic so the model can ask for a missing city and then nothing is required; if the model skips a required tool one extra round forces it, and `get_route` gets its own one extra round because it needs the coordinates; if trains or buses fail or find nothing the answer says so for that mode and keeps the other results, if geocode or `get_route` fails the map is left out, and the fixed "could not check live information" reply is **never** used in route mode); email none. **For explore only (not itinerary or route) the first model call is forced to be `web_search` and nothing else** (`FORCE_WEB_SEARCH_FIRST = True` in `agent.py`: `tool_choice` `allowed_tools`, mode `required`, only `web_search`), so the model can never write anything from its own knowledge before the search has run, and its answer is built from the search results and the other tools (the prompts say: use only what the tools return). This holds for every message in these modes, follow-ups with memory included, except greetings and short confirmations, email mode, and a server without `web_search`. The typical flow is: search (forced), then `geocode_places` and `get_place_images` together, then `get_weather` with the coordinates, then the answer; the round cap is now **6** so one extra forced round still fits. If the model ignores the forcing, its text is dropped and the missing tools (web_search included) are forced; if the search fails, the reply is the fixed one and the model is not asked again. The older switch `FORCE_FIRST_ROUND_WHEN_REQUIRED` (force any required tool) only applies when `FORCE_WEB_SEARCH_FIRST` is off. **Guard:** if the model's first reply is a short clarifying question (at most 300 characters, ending with a question mark) and no tool other than the forced search was used, the check is skipped and the question is returned (audit `decision: guard_skipped`, `reason: clarifying_question`, no text logged). If the model answers too early, the agent drops that draft and runs ONE extra round that forces the missing ones (`allowed_tools`, mode `required`; logged as a `model_decision` with `decision: force_missing_tools` and the tool names). If `web_search` fails (or is still not attempted after the extra round) the reply is the fixed "could not check live information" message, with no further model call; if only weather, map locations or photos failed, the answer is kept and the app adds a note such as "Note: I could not check the weather and the photos right now." **Overall cap:** a whole chat request is limited to `CHAT_REQUEST_TIMEOUT_SECONDS` (default **180**); when it runs out the reply is "Sorry, that took too long. Please try again, or ask in a simpler way." (a normal 200 reply, audit event `request_timeout` with the cap and duration; the MCP connection is closed cleanly). **A `web_search` that answers `timeout`** gets its own reply, "The live search took too long. Please try again." (audit `decision: web_search_timeout`), with no further model call. **A tool that answers `not_configured`** (its key, model or address is missing in `.env`) is reported as a setup problem, not "try again": for `web_search` the reply is "Live search is not set up on this server, so I cannot check live information. Please ask the server administrator to set it up." (audit `decision: web_search_not_configured`, plus a warning that names the missing setting, never a value); for weather, map locations or photos the note says "Note: I could not check the photos: that is not set up on this server." Identical calls in one round (same tool, same arguments, any key order) run once; the duplicates are left out of the conversation and logged as `tool_call` with status `skipped`, error code `duplicate` and argument names only. |

## Getting Started

Start the local services:

```
docker compose up -d
```

Mailpit's web UI is at http://localhost:8025. Docker is not needed for `/chat`. The backend needs MongoDB Atlas: `MONGODB_URI` is **required**, and the app stops at startup with a clear error if it is missing, empty or does not start with `mongodb+srv://` or `mongodb://` (the value is never printed, because it holds a password). Put your Atlas connection string in `MONGODB_URI` in the project-root `.env` (see `.env.example`) and allow your IP in Atlas under Network Access. There is no local MongoDB container any more. Chat history and saved trips will use it later.

Run the backend (from `backend/`, after creating the virtual environment, installing `requirements.txt` and setting `OPENAI_API_KEY` and `OPENAI_MODEL` in the project-root `.env`; see `.env.example`):

```
uvicorn app.main:app --reload
```

Run the chat app (from `frontend/`, in a second terminal; needs Node.js), then open http://localhost:5173:

```
npm install
npm run dev
```

`npm run build` checks that it compiles. The backend must be on http://localhost:8000 (change `VITE_API_URL` in `frontend/.env.local` if not).

Run the backend in Docker instead (from the project root; needs the project-root `.env`, which is mounted read-only into the container, never copied into the image):

```
docker compose build backend
docker compose up -d backend
docker compose exec backend pytest
```

The API is then at http://localhost:8000. Stop it with `docker compose stop backend`.

Run the chat page in Docker too (the React app is built once and served by nginx at http://localhost:5173; `docker compose up -d backend frontend` starts both):

```
docker compose build frontend
docker compose up -d frontend
```

Do not run `npm run dev` at the same time: both use port 5173. After changing the frontend, rebuild with `docker compose build frontend` and `docker compose up -d frontend`. Stop it with `docker compose stop frontend`.
